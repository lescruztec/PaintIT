# Paint IT!

#### Video Demo:  [www.youtube.com/watch?v=jwqzxdJUw64](https://www.youtube.com/watch?v=jwqzxdJUw64)<URL HERE></url>

#### Description:

Paint IT! is a simple web drawing app that allows a user to create drawings, save them and display them and continue to work on them in another time. It features several basic drawing functions such as brush, eraser, zoom, saving as png (with either white/transparent background) and to their own accounts in the app. It also allows user to create canvases with custom resolutions!

#### Files and their purpose:

* app.py - the main file that handles the logic for the server such as serving data and receiving request
* drawing.js - contains the client-side code that handles the logic for drawing and most of the communicating with the server for drawing.html
* styles.css - contains some minimal css that I used
* drawings folder - the storage for the images that gets stored in the server
* helpers.py - contains features that I took from the finance project: login_required decorator and apology function
* index.html - the homepage of the website where the user can create their own canvas and see previous drawings
* drawing.html - the page where the canvas is displayed and the drawing occurs
* draw.db - database of the web app that contains 2 tables: user and drawing
* other htmls (apology.html, login/register, layout) - template files that are necessary for authentication, layout, and minor error-handling features.
* README.md - contains title, video url, and description of this project.
* requirements.txt - contains the libraries or packages needed to run the app.
* placeholder.png - for drawings without image_path (src: [img.magnific.com/free-vector/illustration-gallery-icon_53876-27002.jpg?semt=ais_hybrid&amp;w=740&amp;q=80](https://img.magnific.com/free-vector/illustration-gallery-icon_53876-27002.jpg?semt=ais_hybrid&w=740&q=80))

#### Design Choices:

Before we get down to the basic drawing functionalities, I want to get to the canvas element itself and the design choice as to why I opted to resize the css width and height of it and place it inside canvas-view (a container of sort).  The canvas html element allows you to adjust its actual resolution, aside from the css ones. This decides the image quality of the drawing where as the higher the resolution is, the less pixelated it is and therefore, the lower the quality is. I gave the user the ability to choose whatever resolution they desire in order to fit their needs. The container canvas-view was necessary in oder for the canvas to determine what size it would take form into on the user's screen. I didn't want it to go all the way to whatever resolution the user chose since I didn't want the canvas to overlap with the other html elements or have it become bigger than what the user's screen device can occupy when they first load the canvas or have it be too small for the user to draw on. But of course, this also means that whatever the resolution that they chose, I had to match whatever they are seeing on the screen (the canvas being inside the container) and its actual resolution. This led to some synchronization issues since having the user choose the resolution of the canvas means its coordinate system may not match with whatever its container' resolution has led to become after adjusting to the user's device. This means that I had to translate the current location or position of the mouse pointer of the user so that when they draw, it would be translated accurately to the actual resolution of the canvas, not doing so would lead to a user clicking on one point of the screen and that point leading somewhere else on the canvas. Having more pixels on the canvas also means that a user technically can draw more details on the canvas, so I had to implement a functionality that allows a user to zoom in on the canvas, which of course also means taking into account, once again, resolution. After trying to figure out how to create this functionality along with some help of AI, I learned that zooming in can work if you make the canvas appear larger (obviously), and so that means adjusting the css resolution of the canvas to become bigger. But since this is a drawing tool, it isn't enough to just zoom in or out, you must also zoom to a particular location if you want to draw in a specific place meticulously. So I had to also implement a function where the user can zoom in to where their mouse pointer is at on the screen, but this could also get tiring if you wanted to traverse the canvas while zoomed in but you had to zoom in and out repetitively, so a scrolling function was also a necessary feature that I had to implement. These were the most difficult design choices that I had to figure out how to implement.  I also had to ask for help with AI since aside from figuring out that I had to implement these functionalities, I also needed help with syntax and tutorials on how to actually implement them.

Moving on to some basic features of the app. First, the brush, I kept it simple and made it so that the user can change brush size as they desire and gave them several colors to choose from. The decision was honestly so I could focus on other functions early on the development phase since I didn't want to spend time adding more colors or implementing an actual color palette picker, that also led to me using a drop-down field instead for the colors. As for the eraser, it is implemented the same way as the brush, simply by changing the value of globalCompositeOperation of the 2d context of the canvas to destination-out, which allows a transparent stroke to be drawn on the canvas, effectively erasing an existing stroke if there is any. Just like any drawing application, an undo and redo function were necessary to accomodate for mistakes, which I implemented using a list that acted as a stack. I also decided to allow the user to save their drawing on the Flask server, but I decided for them to save the actual image instead of the strokes despite recording them on the client side since I thought that a user could theoretically fill the server's storage if they wished to do so by trolling and drawing an impossible amount of strokes if I had implemented that in the database. Although this meant that a user couldn't undo their previous strokes if they were to save their drawing on their account and resume it another time, but this was the design choice I made. This decision was accomodated by 2 tables in the database, specifically user and drawing that has a one-to-many relationship, where user_id of the user table is a foreign key in the schema of the drawing table which allows a user to have many drawings. Lastly, I also decided to use the base64 format media type to send images from the server to the client after learning about it from the toDataURL function of the canvas element since I wanted to try it out and implement file handling which was tackled in the previous weeks of the course.
